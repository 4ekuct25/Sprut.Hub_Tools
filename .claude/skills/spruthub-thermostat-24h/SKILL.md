# Суточный отчёт термостата Sprut.Hub

## Где данные (главное)
Числовая история ВСЕХ показаний лежит в архиве **отладочной информации** хаба, НЕ в текстовых логах.

- В web.spruthub.ru карточка датчика показывает только текущее значение (графиков истории нет),
  а WebSocket-API отдаёт лишь текущее состояние — историю оттуда не достать.
- Архив: Настройки → меню «···» (вверху справа) → **Скачать отладочную информацию**
  → `~/Downloads/Sprut.Hub_DevInfo_*.zip` (~10 МБ).
- Внутри: `External/Bridges/History/1/history.duckdb` (+ `.wal` свежий буфер) и
  `segments/YYYY/MM/*.parquet` (по суткам). Таблица `History(timestamp_ms, a_id, s_id, c_id, type, value)`.
  Время в БД — UTC; локальное = +3 ч (MSK).
- Для разбора РЕШЕНИЙ сценария дополнительно: «Скачать логи» → `Sprut.Hub_Log_*.zip`,
  файл `External/spruthub.log`; строки сценария — тег `Automation`, фильтр `Logic_5_Service_42_13`
  (`Эмуляция: target=,current=,temp=N°C`, `реле охлаждения ON`, `Выключатель кондиционера: …`,
  `Проверка датчика: с последнего обновления N мин (timeout 60)`).
  ⚠️ **`spruthub.log` хранит около полусуток.** За всё, что старше, лезть в архивные части
  `External/spruthub.*.log.zip` рядом — их надо распаковать, вместе они дают ~5 суток. Без этого
  «событий нет» означает лишь «лог не достаёт», а не их отсутствие: проверка правки 3.11.6
  по основному файлу дала бы пустой результат, а нужные 14 событий лежали в архивных частях.

## Потоки истории (a_id · s_id · c_id)
- комната (внешний датчик SNZB-02D, вход термостата): `8 · 13 · 15`
- улица (LUMI weather): `17 · 13 · 15`
- датчик самого кондея (внутр., возвратный воздух): `22 · 17 · 21`
- целевая температура, которую сценарий шлёт в кондей: `22 · 17 · 22`
- скорость вентилятора кондея (1..3): `22 · 17 · 24`
- кабинетный VIOMI 9000 (если нужен): `23 · 17 · 21`
- **двери-герконы** (нагрузка на кондей): id=4 «Дверь кухня» (Aqara MCCGQ11LM, serial 00158D0009F5C5A7), также id=5/24. `c_id=15`, значение 1=открыто. Скрипт подсвечивает состояние двери агрегированно (бакеты по `--door-bucket` мин, порог `--door-thresh`; дефолт 30м/0.5 — частые открыл/закрыл схлопываются в основное состояние) и печатает % открытости за окно; набор — словарь `DOORS` вверху скрипта. ContactSensor шлёт ТОЛЬКО изменения — состояние реконструируется непрерывно (затравка последним событием + перенос через сутки), не фильтром по дню.

ID стабильны для этих устройств. Если хаб перепривязывали — проверить `python3 scripts/thermo24.py --list`
и поправить словарь `STREAMS` вверху скрипта.

## Грабли
- **Таймзона DuckDB:** фильтровать историю ПО СЫРЫМ мс (`where timestamp>{lo}`), не через `to_timestamp(ts/1000+off)` со сравнением с датой-строкой — не-UTC сессия сдвигает границы окна и режет события (был баг: фантом «дверь открыта до 00:00»). Скрипт ставит `SET TimeZone='UTC'` и конвертит в локаль только в Python.
- **Свежая распаковка:** DevInfo распаковывать в уникальную tempfile-папку (`thermo24.open_history(zip)`), не в фиксированный путь в маунте — там `rm -rf` может не сработать и прочитаются устаревшие данные (реально проанализировал обрезанные сутки из-за этого).
- **Датчики-состояния (двери-герконы):** ContactSensor шлёт только изменения; состояние в момент X = последнее событие до X. Реконструировать непрерывно (затравка + перенос через сутки), не фильтром по дню.

## Как сделать отчёт
1. Убедиться, что в `~/Downloads` есть свежий `Sprut.Hub_DevInfo_*.zip`. Если нет/старый — скачать
   из хаба через браузер (Claude in Chrome): Настройки → «···» → «Скачать отладочную информацию»
   (и при необходимости «Скачать логи»). Внимание: плитка «Кондиционер» — это быстрый
   ВЫКЛЮЧАТЕЛЬ, не открывай её кликом.

   **Архивы — расходный материал, убирать за собой в тот же заход.** Браузер кладёт их в
   `~/Downloads`, перенаправить его нельзя, поэтому сразу после разбора перенести отработавшие
   архивы в отдельную папку и удалить её:
   ```bash
   WORK=$(mktemp -d /tmp/spruthub_XXXX)
   find ~/Downloads -maxdepth 1 -name 'Sprut.Hub_*.zip' -exec mv {} "$WORK"/ \;
   ls "$WORK"                          # ПРОВЕРИТЬ, что перенос состоялся
   # …разбор идёт по файлам в $WORK — скрипт сам возьмёт оттуда самый свежий:
   python3 scripts/thermo24.py --downloads "$WORK"
   rm -rf "$WORK"                      # в конце захода, когда выводы уже записаны
   ```
   ⚠️ Перенос делать через `find`, а НЕ `mv ~/Downloads/Sprut.Hub_DevInfo_*.zip
   ~/Downloads/Sprut.Hub_Log_*.zip "$WORK"/`: в zsh, если хотя бы одна маска ничего не нашла
   (например, лог не качали), команда отменяется ЦЕЛИКОМ и не переносит ничего — а дальше всё
   молча падает на «не найден DevInfo». Проверено, ловушка настоящая.
   Правила: удалять ТОЛЬКО архивы хаба и только свои распаковки, `~/Downloads` целиком не трогать;
   удалять после того, как выводы попали в ответ и журнал, а не до; графики из `charts/` при этом
   не удалять — они живут по своему правилу (см. шапку `JOURNAL.md`).
   Если архив ещё может понадобиться в этом же заходе — оставить и убрать в конце.
2. Запустить скрипт (он сам берёт самый свежий DevInfo, выгружает 24 ч и строит единый график):
   ```
   pip install duckdb matplotlib --break-system-packages
   python3 scripts/thermo24.py                       # последние 24 ч
   python3 scripts/thermo24.py --from 08:00 --to 20:00   # дневное окно
   python3 scripts/thermo24.py --since 2026-08-16    # многодневное окно датой (ось X — по суткам)
   python3 scripts/thermo24.py --list                # показать доступные потоки
   python3 scripts/thermo24.py --options             # живые опции сценария (hysteresis, fanTempStep…)
   ```
   PNG сохраняется в `./charts/` (папка создаётся; переопределить `--outdir`/`--out`).
   Запускать из корня проекта `SH_VirtualThermostat`, чтобы график лёг в `charts/`.
   Цель и коридор скрипт берёт из живых данных (история 42.13 c_id=18 + гистерезис из опций)
   и печатает строкой «цель за окно … | коридор ±…» — эту строку и цитировать в сводке.
   `--options` печатает настроенные экземпляры первыми; блок с пометкой «НЕ НАСТРОЕН» —
   незаполненная заготовка с дефолтами, для анализа не годится.
3. Показать график пользователю и дать короткую сводку: держался ли коридор вокруг ФАКТИЧЕСКОЙ
   цели, глубина и причина провалов, число/окна активного охлаждения, пик улицы, заряд батареи.
   Перед выводами применить поправки из «Прод-контекста» — без них сводка будет уверенной и неверной.

**Не обрезать вывод диагностики `head`-ом, пока не знаешь, сколько записей она возвращает.**
Усечение выглядит как «данных нет» и порождает ложный диагноз: так `--options` однажды был
объявлен сломанным, хотя печатал оба блока и второй был правильным.

## Прод-контекст

**Здесь намеренно нет чисел настроек.** Цель, гистерезис, силу и упреждение пользователь меняет
когда угодно (за июль–сентябрь 2026 цель прошла 24.3 → 24.4 → 24.0 → 25.0 → 24.6, упреждение
0.2 → 0, силу 2.0 → 1.0). Любой снимок значений в этом файле устаревает за недели и потом врёт
увереннее, чем помогает. Живые значения брать `--options`, цель — из истории 42.13 c_id=18.
Скрипт и то и другое делает сам и печатает строкой «цель за окно … | коридор ±…».

Сценарий — Logic 5, привязан к 42.13. Версия в хабе НЕ обязана совпадать с репо: сверять
`SprutHub.data` (самая поздняя запись `version:` по позиции в файле — свежая, предыдущая остаётся
историческим слепком HSQLDB).

Целевая кондея «инвертирована»: чем сильнее перегрев комнаты, тем ниже setpoint шлётся в VIOMI.

### Обязательные поправки при разборе (каждая оплачена ложным выводом)

- **Считать только внутри «термостат включён»** (42.13 c_id=16: 0=выкл, 2=охлаждение). Его
  выключают регулярно — бывало 27% времени за две недели. Иначе пассивный дрейф выключенной
  комнаты засчитывается сценарию как промах. На графике вкл/выкл не отображается — это ловушка.
- **Отклонение считать от цели, ДЕЙСТВОВАВШЕЙ в этот момент**, а не от последней: внутри одного
  окна цель меняли по нескольку раз.
- **«Комната ниже цели» ≠ «сценарий переохлаждает».** Разложить время недолёта по состоянию
  кондиционера: выключен (пассивное остывание) / включён без спроса на компрессор / компрессор
  тянет. 18.09.2026 при улице 13° «недолёт 81% времени» оказался на 98% пассивным остыванием —
  поднять температуру сценарию нечем, реле нагрева не настроено, режим Охлаждение.
- **Погода — конфаундер.** Сравнивать периоды только в сопоставимых бакетах уличной температуры,
  иначе «стало лучше» означает «потеплело».
- **Решения сценария не восстанавливать по округлённым числам из лога:** разница печатается через
  `toFixed(2)`, и реконструкция по ней даёт ложные «расхождения с формулой». Сверять с допуском,
  границы проверять на исходных парах температур.

Батарея внешнего датчика — следить: при разряде растут паузы обновления (timeout 60 мин →
возможен ложный «потерян датчик»). Молчание живого Zigbee-датчика отказом НЕ считается.
